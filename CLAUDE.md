# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Road to Goals is a static study planner. Users create plans (called `Goal` in code) with optional daily study hours; a plan starts Not started, and pressing Start begins it with an optional deadline, collect resources (read, watch, listen, course, practice, project, workout, habit, task or other) under them, optionally group them into phases, and follow them on a snake-shaped "preparation journey". Progress is weighted by estimated hours, never by resource count. Vite + React 18 + TypeScript (strict) + Zustand + Zod + Supabase + lucide-react, deployed as a static site (see Commands). Data lives in Supabase (Postgres with Row Level Security, signed-in users only) behind backend-independent repository and auth interfaces. Only the auth session, the theme and a running study timer stay in the browser.

`legacy/index.html` is the original single-file version, kept only for comparison. Don't edit it.

## Commands

```bash
npm run dev                         # dev server at /
npm test                            # Vitest, all unit tests
npx vitest run src/domain/schedule.test.ts   # one test file
npx vitest run -t "splits long units"        # tests matching a name
npm run test:e2e                    # Playwright (builds with --mode e2e, in-memory backend, serves dist at :4173/)
npm run lint && npm run typecheck && npm run format:check
npm run build
```

CI (`.github/workflows/ci.yml`) runs all of the above. Cloudflare builds production (roadtogoals.com) from `wrangler.jsonc`, which also handles the SPA fallback there. `deploy.yml` publishes `dist/` to GitHub Pages, the dev site at nabeelarif.github.io/prepline/, on push to `main` or `redesign`, or by manual run on an allowed branch, passing the `VITE_SUPABASE_*` repository variables to the build and the Pages subpath as Vite's `--base`. `base` in `vite.config.ts` is `/`, so full links must be built with `appUrl()` (`src/routes.ts`), and any other root-relative address must include the base. GitHub Pages cannot rewrite URLs, so the build copies `index.html` to `404.html` (`spaFallback` in `vite.config.ts`); Pages serves that for `/prepline/plans/abc`, and the router reads the address.

## Architecture

Layers, in dependency order. Lower layers never import higher ones.

- **`src/domain/`**: pure functions, no React. Types (`types.ts`), date helpers on local `YYYY-MM-DD` strings (`dates.ts`; never use UTC/`toISOString`), URL heuristics, and the calculations:
  - `resources.ts`: `resTotal` / `resDone` / `isDone` / `resStatus`. Durations are stored in minutes and shown as hours. `done` credits the full estimate; otherwise `doneMinutes` is partial progress. Status is derived, never stored: Completed when `done`, In Progress when `startedAt` is set or any time is recorded (so starting credits nothing), else Not Started. Any number of resources can be In Progress. All status moves go through `statusPatch()` / `progressPatch()` (reopen restores earlier partial progress; Not Started clears it, and the UI confirms first via `statusLosesProgress()`). `focusResource()` picks what Continue Learning shows.
  - `metrics(resources)`: weighted progress over any list (plan, phase, or one resource). Every progress figure in the UI goes through it; don't recompute progress elsewhere.
  - Plan schedule: `startDate` null means not started (the user presses Start, which may add a deadline); started with no `targetDate` is open; with one it is scheduled. A deadline only exists on a started plan (`schema.ts` and `updateGoal` keep it so). Both dates are per-user, nullable, and not plan content. Plans loaded with a deadline and no start count as started since `createdAt` (`schema.ts`).
  - `pace()`: schedule feasibility (on track / at risk / behind). Not-started and open plans report kinds `not_started` / `open` with no deadline maths and no red styling. Without `hoursPerDay` it reports only the required pace.
  - `roadmap.ts`: `roadmap(goal, view)` builds journey steps (resources, or phases plus an "Unorganized" group) with states `done` / `active` / `upcoming` and a separate `next` flag (the first unfinished step in priority order, independent of status); `snakeLayout(n, width)` is the pure geometry (columns by width, marker points, SVG segments, U-turns). Components only draw what it returns.
  - Order in `goal.resources` is priority order and drives the journey. `goal.phases` order is display order only. Resources point to phases by `phaseId` (null = no phase); phases are optional.
- **`src/domain/schema.ts`**: Zod schemas that replace the legacy `normalize()`. They are deliberately lenient: every field uses the `field()` helper so missing or bad values fall back to defaults instead of failing. All data from storage or imported backups goes through `parseAppData()`. **Any new persisted field must be added here**, or it is dropped on reload/import. Zod 4 rejects missing keys unless the field is `.optional()`, which `field()` handles. It also migrates older data: course `sections` fold into `minutes`/`doneMinutes`, `rating` and `sample` are dropped, and `phaseId`s pointing at missing phases become null. Imported plan files go through `previewImport()` instead, which rejects non-Road to Goals or other-version files and lists every repair so the user confirms before data is replaced. A plan in a file may carry an optional `sharing` (`{visibility, tags}`, see `readImportSharing` in `share.ts`); it is not stored on `Goal`: `previewImport()` returns it as `shares`, the review lists it under "Will be shared", and `addPlans(data, shares)` applies it through `setPlanSharing` after the plans are saved (a failure there never undoes the import). `docs/agent-plan-format.md` tells AI agents how to write an importable plan file (the `create-roadtogoals-plan` skill in `.claude/skills/` bundles a copy: run `npm run sync-skill` after changing it; a test fails when they differ); when fields, limits, types or defaults change, update it too (`schema.test.ts` checks that its example, `docs/examples/ios-interview-prep.json`, imports with no repairs and matches the document).
- **`src/repositories/`, `src/auth/`, `src/backend/`**: the replaceable backend. `AppRepository` (`repositories/types.ts`) is the app's whole view of durable storage: row-level operations (`saveResource`, `reorderResources`, `deletePhase`, ...) plus atomic `saveGoalTree`, `addGoals`, `deleteAll`. Writes are idempotent upserts by id. Failures are `RepositoryError` with a code (`network`, `unauthorized`, ...). `AuthService` (`auth/types.ts`, including `deleteAccount`, which calls the `delete_account` RPC (SECURITY DEFINER, deletes the `auth.users` row; everything cascades) and clears the local session, including the password-reset return trip: `onPasswordRecovery` sets `recovery`, and `NewPasswordScreen` calls `updatePassword`) is provider-neutral (`AuthProviderId` = google | x | password), with linking, and failures are `AuthError`. `backend/index.ts` is the one place that picks the backend from env (`createBackend`), and a missing config is an error screen, never a browser-storage fallback. `backend/supabase/` is the only code that imports `@supabase/*` (ESLint and `architecture.test.ts` enforce it): `rows.ts` maps rows and function results (including the sharing ones) to domain models, `repository.ts` holds table names and RPCs, `errors.ts` maps errors. `backend/memory/` is an in-memory backend for Vitest (`MODE=test`) and the e2e build (`--mode e2e`) only. To change backend, implement both interfaces, pass `repositories/contract.ts`, and switch `createBackend`. SQL lives in `supabase/schema.sql`, the single initial schema (no migrations until production exists; later changes become ordered files in `supabase/migrations/`) (RLS: every row has `user_id`, composite keys `(user_id, id)`; order is a `position` column; RPCs are `SECURITY INVOKER`), with pgTAP tests in `supabase/tests/`. Setup is in `docs/supabase-setup.md`. A new persisted field needs a column in `schema.sql`, `rows.ts`, the RPC payloads, and `schema.ts`. Plan content and the owner's own state are separate tables: `goals` / `phases` / `resources` are content only; `plan_settings` holds the user's `start_date`, `target_date` and `hours_per_day`; `resource_progress` holds `done`, `done_minutes`, `done_at`, `started_at` (a missing row means not started, and saving a resource with no progress deletes the row). The RPC payloads and `load_all_data` keep the flat shape, so the app and `rows.ts` don't see the split. Anything shown to other people must read the content tables only.
- **Link auto-fill** (`supabase/functions/enrich-url`, `repositories/enrich.ts`, `backend/supabase/enrich.ts`, `ResourceForm`): the browser cannot fetch other sites (CORS), so a Deno Edge Function reads a pasted link. YouTube (Data API when `YOUTUBE_API_KEY` is set, else oEmbed title only), Vimeo (oEmbed) and other pages (Open Graph / `<title>`, estimated reading time) return `{title?, minutes?, readMinutes?}` (`minutes` is a real video length; `readMinutes` is a text-based estimate the form uses only for a Read, so a course page never understates its hours); no third-party scraping libraries. It needs a signed-in user and refuses non-http(s), odd ports and local/private addresses (also after DNS and on every redirect; a DNS-rebinding gap between check and fetch is accepted). `Backend.enricher` (`UrlEnricher`, never throws, null when nothing is found) feeds store `fetchUrlInfo`; the form guesses from the address at once (`detectType`, `titleFromUrl`), then fills only fields the user has not set. The parser is pure (`parse.ts`, tested by Vitest via the `supabase/functions` include); the memory backend answers only what `setUrlInfo` registered. Setup is in `docs/supabase-setup.md`.
- **Use your own AI** (`domain/aiPrompt.ts`, `domain/planText.ts`, `forms/AiPlanPanel.tsx`, `public/ai/`): the app makes no AI calls; users take a prompt to their own AI and paste the reply back. `aiPrompt.ts` builds the prompt (a link to the hosted skill plus the form's settings) and holds `AI_PROVIDERS`, the one place to add or fix an AI: those with a `promptParam` get a prefill link while it stays under `MAX_PREFILL_URL`, the rest only open, and the prompt is copied in every case because the prefill parameters are undocumented. "Copy full instructions" sends the hosted skill's own text, so there is one source. `planText.ts` `readPlanText()` is the only way text becomes a plan, for pasted replies and chosen files alike: it finds the JSON, repairs curly quotes and trailing commas outside strings, explains cut-off or shortened replies, then calls `previewImport()` (whose `errors` lists every problem, for the "Copy fix-it message"). It has no DOM dependency, so a later MCP `create_plan` tool can use the same checks and `mergePlans()`. `public/ai/skill-v1.md` (with `plan-schema-v1.json` and `example-plan-v1.json`) is public, read by AI fetchers without JavaScript; `public/_headers` (Cloudflare) sets its type and CORS, and `robots.txt` allows the fetchers. **Never change a published versioned file in a breaking way**: add `skill-v2.md`, point `AI_SKILL_PATH`, `llms.txt` and `scripts/sync-skill.mjs` at it, and run `npm run sync-skill` to refresh `skill.md`. `domain/aiFiles.test.ts` keeps these files in step with the app's types, colours, limits and importer; when fields change, update them along with `docs/agent-plan-format.md`.
- **Study log** (`src/domain/studyLog.ts`, `study_log` table, `AppRepository.loadStudyLog` / `saveStudyDay`): minutes studied per local day, for the streak and the heatmap (the streak in the top bar and `StreakPage` at `/streak`, a year-long grid). It is the user's own history, not plan content: one row per `(user_id, day)`, kept when plans are deleted and cleared by Delete All Data, never in `AppData`, backups or shared plans. `commit()` feeds it: `studyDelta(prev, next, today)` sums the change in each existing resource's one-day tally (`loggedOn`/`loggedMinutes`), `addStudy` applies it to `store.studyLog.days`, and one keyed op saves the day's new **total** (`save_study_day`, absolute, so a retry never counts twice; zero removes the day). `studyLog.ready` is false until loaded, and nothing is added or saved while it is (a failed load shows 0 in the top bar and an "unavailable" note on the page). Only the last `STUDY_LOG_DAYS` (371) days load, so streaks are capped at that. A streak survives an empty today until the day ends.
- **Study timer** (`src/domain/timer.ts`, `src/state/timer.ts`, `TimerButton`, `TimerBar`): a start/stop timer on a resource, optionally Pomodoro (fixed 25 min focus / 5 min break; only focus is credited). The running timer (`{userId, goalId, resourceId, startedAt, mode}`) lives in its own `useTimer` store and `localStorage` key `roadtogoals:timer`, like the theme: per browser, not in `AppData`, backups or the backend. Elapsed time is always computed from `Date.now() - startedAt`, so a reload resumes it. Stop calls `addStudyMinutes(goalId, resourceId, minutes)`, which goes through `progressPatch()` and `commit()`, so `doneMinutes`, the one-day tally and the study log follow exactly as for manual entry (progress clamps at the estimate, so time beyond it is not logged). Stop is refused, and the timer keeps running, while `studyLog.ready` is false. One session credits at most 4 h, all to the day it is stopped. A stored timer for another user is ignored and sign-out clears it.
- **Sharing** (`src/domain/share.ts`, `repositories/sharing.ts`, `backend/supabase/sharing.ts`, `backend/memory`): a plan is `private` (default), `unlisted` (anyone with the link) or `public` (also in Explore). `PlanSharingRepository` is separate from `AppRepository` because `getShared` and `listPublic` work signed out; `Backend` is `{ repo, sharing, auth }`. Other people only ever get **content** (`SharedPlan`: title, description, phases, resources with title/url/type/minutes/notes), never progress, dates or daily hours: the Supabase functions `get_shared_plan` / `list_public_plans` (SECURITY DEFINER, explicit columns, never joining `plan_settings` or `resource_progress`) are the only public read path, `anon` still has no table access, and `plan_shares` can only be written through definer functions so owners cannot edit `hidden` (moderator takedown, set in SQL) or `copy_count`. `plan_shares`/`plan_copies`/`plan_favorites`/`plan_reports` cascade from the plan, so deleting or replacing a plan stops sharing it. The author is the owner's `profiles.display_name`, joined when the plan is read (never copied onto the plan), so renaming the account renames the author everywhere. Every account has a name: `handle_new_user` uses the one given at sign-up, else the provider's name (`full_name` for Google, or `name`), otherwise `random_display_name()` (adjective, noun and 00-99, e.g. "Curious Pathfinder 42"; the word lists are also in `randomDisplayName` in `domain/share.ts` for the in-memory backend, keep them in step), and the user can change it in Account settings. The sharing dialogs never ask for a name; `set_plan_sharing` takes no name (max 20 public plans). A plan can be shared while empty (the create dialog offers sharing), but `list_public_plans` only lists it once it has a resource; `setPlanSharing` waits for queued saves so a just-created plan exists first. **Favorites**: a signed-in user stars a shared plan (`set_plan_favorite(slug, on)`, idempotent, own and taken-down plans ignored) so they can find it later without copying; `plan_favorites` has one row per person and plan, no policy, and the count is derived (`count(*)`, never stored, because it can go down). `get_shared_plan`, `list_public_plans` and `similar_plans` return `favorite_count` and `favorited` (the caller's own star; false signed out), owners get their counts from `my_favorite_counts` (counts only, never who; `PlanSharing.favoriteCount`), `list_my_favorites` lists the caller's stars newest first (unlisted plans included, taken-down ones not), and a plan the owner makes private drops out of everyone's favorites. `useFavorite` (optimistic, rolls back; signed out it calls `useRequestSignIn`) drives `FavoriteButton` on `PlanCard` and the shared page (hidden on your own plan), both of which always show `N forks · N favorites`; `FavoritesPage` is the signed-in `/favorites` route. `/streak` is the study-log page. Explore lists by newest, most copied or most favorited (`PublicSort`), searches name, description and tags, shows popular tags (`list_popular_tags`) and, on a shared plan, similar plans by tag overlap (`similar_plans`); search, tag and sort live in the URL. A copy records `Goal.source` (`{slug, name}`, stored in `goals.source_slug/source_name`, so it is plan content, and cleared by `previewImport`); the dashboard shows "Forked from", and once the copy is shared the public functions return it as `source` (`{slug, name, available}` via `plan_origin`; the original's `slug` is given only while it is public, so a copy never reveals an unlisted or private original: `available` is false, `slug` null, and only the title it had is shown) and Explore cards and the shared page show "Forked from", linking to the original while it is available. Copies start private; nothing stops the owner making one public later. The original's slug on every copy is the analytics key (`goals.source_slug`). The viewer's own plans are recognised in Explore by matching the slug against `store.sharing.plans` (`useOwnPlanId`): cards say "by you" (`.by-you`, accent color), and the shared page replaces Add to My Plans with a link to the plan. A viewer copies a plan (`copyOfSharedPlan` then `mergePlans` and `repo.addGoals`, via store `copySharedPlan`): fresh ids, not started, no deadline, no progress; there is no live link between copy and original. The shared plan is live: owner edits show at once. The contract suite `describeSharingContract` (in `repositories/contract.ts`) checks the no-leak rule for every implementation. `store.sharing` (status, plans by id, displayName) loads alongside the data and is not part of `commit`.
- **`src/state/store.ts`**: one Zustand store, `createAppStore({ repo, auth })`; the module-level `useStore` is wired via `createBackend(import.meta.env)`. `data` (`AppData`) is changed only through `commit(recipe, ui?)`: the Immer recipe applies in memory at once, then `diffData()` (`syncOps.ts`) turns the before/after difference into row-level repository ops, which go through `WriteQueue` (`writeQueue.ts`): serial, in order, so an older save never overwrites a newer one; a failed op halts the queue, keeps every edit in memory, and `retrySync()` resumes (a write the server rejected for good, `validation` or `conflict`, is not retryable: `sync.retryable` is false and the banner offers `discardUnsaved()`, which drops the queue and reloads; `reload()` itself refuses while writes are unconfirmed, and `commit()` is ignored while `busy`) (`sync.status` is idle/saving/saved/error; "saved" means the backend confirmed). A `toast` in a commit's `ui` patch is shown only after confirmation. Whole replacements (`addPlans`, `deleteAllData`; `addPlans` appends through `repo.addGoals` and never rewrites saved plans) are async and non-optimistic through `replaceData`: they wait for the queue (`exclusive`), call one atomic repo method, and touch memory only on success; `busy` blocks a second one. `auth`, `load` (`error` is not the same as empty) and `sync` are in the store; a user change clears data, ui and the queue (`handleUser`). `ui` (journey view, filters, selected resource, open overlay, toast) is never persisted. The screen is not in the store: the URL decides it (react-router, `BrowserRouter` in `main.tsx`; addresses in `src/routes.ts`): `/` redirects to `/dashboard` (or to the page asked for before an OAuth sign-in, remembered by `rememberReturnPath`), `/dashboard` shows the current plan, `/plans` is My Plans, `/explore` and `/explore/:slug` are the public gallery and one shared plan: they work signed out (`PublicShell` in `App.tsx`, shown before `AuthGate`; "Sign in" and "Add to My Plans" call `useRequestSignIn`, which remembers the page and opens `/signin`, and signing in returns to the page; the two pages load lazily), and are also routes inside `Shell` with an Explore nav link (`exploreRoutes` is shared by both shells). `/plans/:planId` is one plan (`PlanPage` makes it the current plan via `selectGoal`, and shows "Plan not found" for an id not in the user's data, which is also how another user's plan looks under RLS). Top bar items are `NavLink`s; navigate with `Link` / `useNavigate`, never a store action. Signed-out users see `AuthGate` at whatever address they asked for, so signing in lands on it. Tests render the app with `renderApp(at)` (`src/test/renderApp.tsx`). `createEmptyAppData()` in `src/domain/backup.ts` is the one empty state. `App` shows config error, sign-in (`AuthGate`), loading or load-error screens before the app.
- **`src/components/`**: React components that read the store via selectors; actions are taken from `useStore.getState()` or selectors. `GoalView` (the dashboard) computes metrics, pace and journey nodes once per render and passes them down, in the order plan header with the weighted progress bar (`PlanBox`), the next step (`ContinueCard`), the journey, the pace and time-by-type block, then the resources. `Shell` and `PublicShell` start with a skip link to `#main`; the tab title is set per page through `usePageTitle` and `src/pageTitle.ts`, which also holds the study timer's clock prefix so the two never overwrite each other. Overlays (plan, resource, phase, resource details, backup) are chosen by `ui.overlay` in `App.tsx` and wrapped in `Overlay` (focus trap, Escape, scroll lock); each names itself with an `h2 id={DIALOG_TITLE}`. Dropdowns use `Menu` (keyboard and outside-click handling). The resource list (`ResourceList.tsx`) is grouped into a `PhaseBand` per phase in phase order, then "Unassigned" (with a Create phase button when the plan has no phases), each followed by `ResourceCard`s; finished phases start folded. Picking a phase on the journey (`jumpToPhase`) never filters the list: that band opens and scrolls into view, and every band stays foldable. Cards reorder within their band by dragging a handle (`useReorderDrag`: pointer events for mouse and touch, arrow keys on the handle) via `placeResource`, which drops next to a visible row so filtered lists still work; moving to another phase goes through the card's menu or Assign phase. Destructive actions use `ConfirmButton` (click twice within 4s), also inside menus via the `confirm` item option. The import overlay (`forms/DataPanel.tsx`, `ui.overlay` kind `import` with `source` `paste` or `file`, opened from the account menu, My Plans, the welcome screen and the AI dialog) is the exception: an explicit state machine (`useRestoreFlow`: paste or pick → check → review → result) with two tabs, Paste plan (`PasteCard`) and From a file (`.json` only). Review shows each plan's size and first three resources. At review the user picks Add to My Plans, which runs at once and appends the plans with fresh ids (`mergePlans` in `domain/backup.ts`); there is no download or replace. A pasted plan then opens at its own page; a file, or a sharing failure, ends on the result screen. The AI dialog (kind `ai`) keeps its form in `ui.aiForm` while the user goes to paste. Export is per plan (`domain/exportPlan.ts`, menus from `components/exportMenu.tsx`, in the My Plans card menu and the plan header): JSON is an importable plan file with content only (no progress, dates or fork source; `sharing` only when the plan is shared), Markdown is an outline, and PDF prints a standalone HTML page through a hidden frame (`downloadFile.ts`), with no PDF library. Delete All Data and Delete Account sit under Privacy in Account settings (`forms/AccountPanel.tsx`), with confirmations in `ConfirmPanel`, where Escape cancels only the confirmation (it calls `preventDefault()`, which `Overlay` respects). The top bar (`TopBar.tsx`) holds the nav, an icon-only save indicator and `AccountMenu` (avatar menu: email, theme, Import plans, Account settings, Sign out). Sign-in methods are in `forms/AccountPanel.tsx` (overlay `account`); `SyncBanner` shows failed saves with Retry. Backup files add an `exportedAt` key that loading ignores: local time with its UTC offset (`2026-10-28T14:32:05+05:00`), shown in the viewer's time zone on review. A file may also carry `generatedBy` (`{tool, model, skill}`, read by `generatedByOf`, shown as "Made by" on review, never stored); the `create-roadtogoals-plan` skill writes both. Icons come from `lucide-react`.
  My Plans labels each plan from `planStatus()` (`domain/schedule.ts`: completed, else not started without a `startDate`, else in progress); there is no "current" label, though `activeGoalId` still picks the Dashboard's plan. Public cards show `shareCounts()`, re-read on each visit through `refreshSharing()`. Today (`TodayView`) shows every plan in progress from `dayAgenda()`, one card each, with a single ring that counts each plan only up to its daily budget, or the work it had left if that is less (a plan finished today stays for the day). A deadline-only budget is the pace for the work left when the day began. It steps from today to six days ahead (`?day=1`..`6`); later days are read-only and assume the earlier ones were done. Because Today acts on any plan, the store's resource actions and the resource overlays find the owning plan by resource id; adding, reordering and phase actions still act on the current plan.
- **`src/styles/`**: global CSS split by area, imported in order from `index.css` (`responsive.css` must stay last). Class names are global, not CSS Modules. Colors are custom properties in `tokens.css`, the Trailhead palette (pine `--accent` for actions and finished work, lake `--prog` for in progress, summit amber `--next` for the single next step, flag red `--bad` for real schedule risk only, a deep pine top bar `--side-bg`, type colors `--t-*`, phase colors `--ph-*`), plus type, radius, spacing, motion and touch-size tokens (`--f-display` Newsreader for titles, `--f-body` Plus Jakarta Sans, `--fs-*`, `--r-*`, `--s-*`, `--t-fast/base/slow`, `--hit`) with dark-mode overrides; use the tokens, not literal colors. The light, OS-dark and `[data-theme='dark']` blocks are the same palette written three times, so change them together. `PRODUCT.md` and `DESIGN.md` at the root record the product facts and the visual system (rules, named doctrines, components). Dark follows the OS unless `[data-theme]` on `<html>` overrides it; `src/theme.ts` sets that from the theme options in the top bar's account menu and saves it under `roadtogoals:theme`, separate from app data and backups; it also keeps the two `theme-color` meta tags in `index.html` in step with the choice. Below 680px the top bar nav collapses behind a hamburger button (`.nav-toggle` in `TopBar.tsx`, a dropdown that closes on navigation, Escape or an outside click), menus open as bottom sheets, and the resource table becomes stacked cards; where the pointer is coarse every control gets a 44px target (`@media (pointer: coarse)` in `responsive.css`); below 560px the journey becomes a vertical stepper and modals become bottom sheets.

## Testing notes

- `src/test/harness.ts` (`resetApp(data)`, `memory()`, `serverData()`) puts the global store in a known state against the in-memory backend and lets tests inject failures (`failNext`, `hold`); store tests build their own store with `createMemoryBackend()`. `repositories/contract.ts` is a behaviour suite every `AppRepository` must pass (`backend/supabase/live.test.ts` runs it against a real project when `SUPABASE_TEST_*` env vars are set). `src/test/setup.ts` replaces `localStorage` with an in-memory one, because Node 25+'s built-in `localStorage` shadows jsdom's.
- Unit tests sit next to the code (`*.test.ts[x]`); browser tests live in `e2e/`. `src/test/fixtures.ts` has `res()` / `goal()` builders for domain tests.
