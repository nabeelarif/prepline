# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Road to Goals is a static study planner. Users create plans (called `Goal` in code) with a target date and optional daily study hours, collect articles, videos, courses and practice under them, optionally group them into phases, and follow them on a snake-shaped "preparation journey". Progress is weighted by estimated hours, never by resource count. Vite + React 18 + TypeScript (strict) + Zustand + Zod + Supabase + lucide-react, deployed to GitHub Pages by GitHub Actions. Data lives in Supabase (Postgres with Row Level Security, signed-in users only) behind backend-independent repository and auth interfaces. Only the auth session and the theme stay in the browser.

`legacy/index.html` is the original single-file version, kept only for comparison. Don't edit it.

## Commands

```bash
npm run dev                         # dev server at /
npm test                            # Vitest, all unit tests
npx vitest run src/domain/schedule.test.ts   # one test file
npx vitest run -t "splits long units"        # tests matching a name
npm run test:e2e                    # Playwright (builds with --mode e2e, in-memory backend, serves dist at :4173/)
npm run lint && npm run typecheck && npm run format:check
npm run build
```

CI (`.github/workflows/ci.yml`) runs all of the above; `deploy.yml` publishes `dist/` to Pages on push to `main`. `deploy.yml` passes the `VITE_SUPABASE_*` repository variables to the build. `base` in `vite.config.ts` is `/` because the site is served from the custom domain roadtogoals.com (`public/CNAME`).

## Architecture

Layers, in dependency order. Lower layers never import higher ones.

- **`src/domain/`**: pure functions, no React. Types (`types.ts`), date helpers on local `YYYY-MM-DD` strings (`dates.ts`; never use UTC/`toISOString`), URL heuristics, and the calculations:
  - `resources.ts`: `resTotal` / `resDone` / `isDone` / `resStatus`. Durations are stored in minutes and shown as hours. `done` credits the full estimate; otherwise `doneMinutes` is partial progress. Status is derived, never stored: Completed when `done`, In Progress when `startedAt` is set or any time is recorded (so starting credits nothing), else Not Started. Any number of resources can be In Progress. All status moves go through `statusPatch()` / `progressPatch()` (reopen restores earlier partial progress; Not Started clears it, and the UI confirms first via `statusLosesProgress()`). `focusResource()` picks what Continue Learning shows.
  - `metrics(resources)`: weighted progress over any list (plan, phase, or one resource). Every progress figure in the UI goes through it; don't recompute progress elsewhere.
  - `pace()`: schedule feasibility (on track / at risk / behind). Without `hoursPerDay` it reports only the required pace.
  - `roadmap.ts`: `roadmap(goal, view)` builds journey steps (resources, or phases plus an "Unorganized" group) with states `done` / `active` / `upcoming` and a separate `next` flag (the first unfinished step in priority order, independent of status); `snakeLayout(n, width)` is the pure geometry (columns by width, marker points, SVG segments, U-turns). Components only draw what it returns.
  - Order in `goal.resources` is priority order and drives the journey. `goal.phases` order is display order only. Resources point to phases by `phaseId` (null = no phase); phases are optional.
- **`src/domain/schema.ts`**: Zod schemas that replace the legacy `normalize()`. They are deliberately lenient: every field uses the `field()` helper so missing or bad values fall back to defaults instead of failing. All data from storage or imported backups goes through `parseAppData()`. **Any new persisted field must be added here**, or it is dropped on reload/import. Zod 4 rejects missing keys unless the field is `.optional()`, which `field()` handles. It also migrates older data: course `sections` fold into `minutes`/`doneMinutes`, `rating` and `sample` are dropped, and `phaseId`s pointing at missing phases become null. Backups go through `previewImport()` instead, which rejects non-Road to Goals or other-version files and lists every repair so the user confirms before data is replaced. `docs/agent-plan-format.md` tells AI agents how to write an importable plan file; when fields, limits, types or defaults change, update it too (`schema.test.ts` checks that its example, `docs/examples/ios-interview-prep.json`, imports with no repairs and matches the document).
- **`src/repositories/`, `src/auth/`, `src/backend/`**: the replaceable backend. `AppRepository` (`repositories/types.ts`) is the app's whole view of durable storage: row-level operations (`saveResource`, `reorderResources`, `deletePhase`, ...) plus atomic `saveGoalTree`, `replaceAll`, `deleteAll`. Writes are idempotent upserts by id. Failures are `RepositoryError` with a code (`network`, `unauthorized`, ...). `AuthService` (`auth/types.ts`, including the password-reset return trip: `onPasswordRecovery` sets `recovery`, and `NewPasswordScreen` calls `updatePassword`) is provider-neutral (`AuthProviderId` = google | x | password), with linking, and failures are `AuthError`. `backend/index.ts` is the one place that picks the backend from env (`createBackend`), and a missing config is an error screen, never a browser-storage fallback. `backend/supabase/` is the only code that imports `@supabase/*` (ESLint and `architecture.test.ts` enforce it): `rows.ts` maps rows to domain models, `repository.ts` holds table names and RPCs, `errors.ts` maps errors. `backend/memory/` is an in-memory backend for Vitest (`MODE=test`) and the e2e build (`--mode e2e`) only. To change backend, implement both interfaces, pass `repositories/contract.ts`, and switch `createBackend`. SQL lives in `supabase/schema.sql`, the single initial schema (no migrations until production exists; later changes become ordered files in `supabase/migrations/`) (RLS: every row has `user_id`, composite keys `(user_id, id)`; order is a `position` column; RPCs are `SECURITY INVOKER`), with pgTAP tests in `supabase/tests/`. Setup is in `docs/supabase-setup.md`. A new persisted field needs a column in `schema.sql`, `rows.ts`, the RPC payloads, and `schema.ts`.
- **`src/state/store.ts`**: one Zustand store, `createAppStore({ repo, auth })`; the module-level `useStore` is wired via `createBackend(import.meta.env)`. `data` (`AppData`) is changed only through `commit(recipe, ui?)`: the Immer recipe applies in memory at once, then `diffData()` (`syncOps.ts`) turns the before/after difference into row-level repository ops, which go through `WriteQueue` (`writeQueue.ts`): serial, in order, so an older save never overwrites a newer one; a failed op halts the queue, keeps every edit in memory, and `retrySync()` resumes (a write the server rejected for good, `validation` or `conflict`, is not retryable: `sync.retryable` is false and the banner offers `discardUnsaved()`, which drops the queue and reloads; `reload()` itself refuses while writes are unconfirmed, and `commit()` is ignored while `busy`) (`sync.status` is idle/saving/saved/error; "saved" means the backend confirmed). A `toast` in a commit's `ui` patch is shown only after confirmation. Whole replacements (`restoreBackup`, `addPlans`, `deleteAllData`; `addPlans` appends through `repo.addGoals` and never rewrites saved plans) are async and non-optimistic through `replaceData`: they wait for the queue (`exclusive`), call one atomic repo method, and touch memory only on success; `busy` blocks a second one. `auth`, `load` (`error` is not the same as empty) and `sync` are in the store; a user change clears data, ui and the queue (`handleUser`). `ui` (page, journey view, filters, selected resource, open overlay, toast, mobile nav) is never persisted. Pages are a `ui.page` value, not routes. `createEmptyAppData()` in `src/domain/backup.ts` is the one empty state. `App` shows config error, sign-in (`AuthGate`), loading or load-error screens before the app.
- **`src/components/`**: React components that read the store via selectors; actions are taken from `useStore.getState()` or selectors. `GoalView` (the dashboard) computes metrics, pace and journey nodes once per render and passes them down. Overlays (plan, resource, phase, resource details, backup) are chosen by `ui.overlay` in `App.tsx` and wrapped in `Overlay` (focus trap, Escape, scroll lock); each names itself with an `h2 id={DIALOG_TITLE}`. Dropdowns use `Menu` (keyboard and outside-click handling). The resource list reorders by dragging a row handle (`useReorderDrag`: pointer events for mouse and touch, arrow keys on the handle) via `placeResource`, which drops next to a visible row so filtered lists still work. Destructive actions use `ConfirmButton` (click twice within 4s), also inside menus via the `confirm` item option. The backup overlay (`forms/DataPanel.tsx`) is the exception: one-click download, restore as an explicit state machine (`useRestoreFlow`: pick → check → review → result). At review the user picks Add to My Plans, which runs at once and appends the file's plans with fresh ids (`mergePlans` in `domain/backup.ts`), or Replace All Data, which needs a confirmation first, and Delete All Data below the two cards, with both confirmations in `ConfirmPanel`, where Escape cancels only the confirmation (it calls `preventDefault()`, which `Overlay` respects). Account and sign-in methods are in `forms/AccountPanel.tsx` (overlay `account`); `SyncBanner` shows failed saves with Retry. Backup files add an `exportedAt` key that loading ignores: local time with its UTC offset (`2026-10-28T14:32:05+05:00`), shown in the viewer's time zone on review. Icons come from `lucide-react`.
- **`src/styles/`**: global CSS split by area, imported in order from `index.css` (`responsive.css` must stay last). Class names are global, not CSS Modules. Colors are custom properties in `tokens.css` (indigo accent, navy sidebar, type colors `--t-*`, phase colors `--ph-*`) with dark-mode overrides; use the tokens, not literal colors. Dark follows the OS unless `[data-theme]` on `<html>` overrides it; `src/theme.ts` sets that from the sidebar's theme switch and saves it under `roadtogoals:theme`, separate from app data and backups. Below 680px the resource table becomes stacked cards; below 560px the journey becomes a vertical stepper and modals become bottom sheets.

## Testing notes

- `src/test/harness.ts` (`resetApp(data)`, `memory()`, `serverData()`) puts the global store in a known state against the in-memory backend and lets tests inject failures (`failNext`, `hold`); store tests build their own store with `createMemoryBackend()`. `repositories/contract.ts` is a behaviour suite every `AppRepository` must pass (`backend/supabase/live.test.ts` runs it against a real project when `SUPABASE_TEST_*` env vars are set). `src/test/setup.ts` replaces `localStorage` with an in-memory one, because Node 25+'s built-in `localStorage` shadows jsdom's.
- Unit tests sit next to the code (`*.test.ts[x]`); browser tests live in `e2e/`. `src/test/fixtures.ts` has `res()` / `goal()` builders for domain tests.
